# BlackBook Wallet Architecture: Multi-Modal Authentication

## The Core Principle: L1 is Dumb, Wallets are Smart

The BlackBook Layer 1 (L1) Proof of History (PoH) blockchain is designed to be a **pure signature-verifying network**. 

L1 does not know what a "wallet session" is. It does not know how a private key is stored. It does not care if a signature was generated by a web browser, a hardware device, or a threshold of servers. 

**The L1 Standard:** Every write operation (transfer, escrow, faucet) submitted to L1 must be accompanied by a standard **Ed25519 Signature**. 

Because L1 only cares about the final signature, we can build a highly flexible, multi-modal wallet ecosystem on top of it. Below are the three primary wallet modes and how they seamlessly connect to BlackBook L1.

---

## Mode 1: Local Signing (The "Phantom" Model)

This is the traditional Web3 wallet approach, suited for browser extensions (like Phantom or MetaMask) or native mobile apps.

### How It Works
1. **Key Generation:** The user generates a BIP-39 mnemonic phrase locally on their device.
2. **Key Storage:** The Ed25519 private key is encrypted (using a user-provided password or biometrics) and stored locally in the device's secure enclave or browser storage.
3. **The UX:** The user clicks "Send", approves the transaction via a UI prompt, and the wallet signs the payload.

### Connection to L1
* The local wallet constructs the standard L1 plaintext message (e.g., `TRANSFER:{pubkey}:{to_address}:{amount}:{timestamp}:{nonce}`).
* The wallet signs this message locally using the unencrypted private key in memory.
* The wallet makes an HTTP POST request directly to the L1 RPC (e.g., `POST /transfer/simple`) with the public key and the resulting hex signature.
* L1 verifies the signature against the provided public key and processes the transaction.

**Best for:** Crypto-native users, DeFi power users, and those holding high balances who demand self-custody.

---

## Mode 2: SSS 2-of-3 (Shamir's Secret Sharing)

This mode bridges the gap between Web2 convenience and Web3 security. It removes the need for mnemonic phrases while maintaining a non-custodial architecture.

### How It Works
1. **Key Generation:** A key is generated in the browser.
2. **The Split:** The Ed25519 private key is split using Shamir's Secret Sharing into 3 shards. Any 2 shards are required to rebuild the key.
   * **Share A:** Encrypted with the user's password and stored on their local device.
   * **Share B:** Stored securely on the BlackBook Wallet Service (a separate, centralized authentication server).
   * **Share C:** Given to the user as a cold-storage recovery hex code.
3. **The UX:** The user "logs in" with a username and password. The browser decrypts Share A, fetches Share B from the server, reconstructs the key in local memory, and signs. (Alternatively, the Wallet Service can hold the reconstructed key in a short-lived memory session).

### Connection to L1
* The signature generation happens **off-chain** (either in the user's browser or on the dedicated Wallet Service server).
* Once the key is temporarily reconstructed, a standard L1 message is signed.
* The signed payload is submitted directly to the L1 node's `POST /transfer/simple`. 
* Because L1 only sees a standard Ed25519 signature, it has no idea that the key was stored in pieces.

**Best for:** Onboarding Web2 users, frictionless gaming integrations, "Invisible Wallet" experiences.

---

## Mode 3: FROST (Flexible Round-Optimized Schnorr Threshold)

FROST provides institutional-grade security. Unlike SSS which requires all key parts to be brought together in one place (reconstructed) to sign a transaction, FROST generates the signature while the key remains fragmented.

### How It Works
1. **Key Generation:** A private key is generated collectively via Multi-Party Computation (MPC). The full key **never exists in a single location at any time**.
2. **The Split:** Shards are distributed among multiple independent signing nodes (e.g., User Device, BlackBook Server, Trusted 3rd Party Co-Signer).
3. **The UX:** A transaction is initiated. A "Coordinator" reaches out to the participating nodes. Each node validates the request (e.g., "Is this transfer under $10,000?") and provides a "partial signature".
4. **The Magic:** The Coordinator aggregates these partial signatures into a single, standard Ed25519 signature. 

### Connection to L1
* The output of the FROST aggregation protocol mathematically matches a standard Ed25519 signature.
* When the combined signature is submitted to the BlackBook L1 node, it looks identical to a Mode 1 local signature. 
* L1 verifies it trivially without knowing that 3 different computers had to mathematically collaborate to create it.

**Best for:** Institutional vaults, high-value corporate treasuries, and automated algorithmic trading where no single server or employee should hold the full key.

## Summary

By relentlessly keeping BlackBook L1 strictly locked to standard signature verification, the chain achieves massive throughput (Sealevel execution) via PoH. 

Complex validation logic (passwords, sessions, rate limits, 2FA, multi-sig consensus) is pushed exclusively to the application layer. This guarantees that **user funds are mathematically secure at the protocol level**, while remaining maximally flexible for front-end developers building diverse onboarding experiences.
