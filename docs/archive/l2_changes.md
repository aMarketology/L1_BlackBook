## What Was Added

### 1. Merkle Proof Claim Flow (Milestone 6) — [FRONTEND + L2 SERVER]

Winners of resolved BB markets can now claim their BB payout from the L1 escrow contract using a Merkle inclusion proof generated by the L2 rollup at resolution time.

**New endpoints:**
- `GET /api/proof/:market/:wallet` — already existed as a Next.js proxy to L2
- `POST /api/markets/:id/claim` — **NEW** — fetches proof from L2, submits to L1 `/escrow/withdraw`

**Request:**
```
POST /api/markets/:id/claim
Content-Type: application/json

{ "wallet": "Base58SolanaPublicKey..." }
```

**Response:**
```json
{
  "success": true,
  "market_id": "MLS-W8-LAFC-MIA",
  "wallet": "9B5X...",
  "payout_bb": 12.5,
  "payout_spl": 12500000,
  "proof_depth": 4,
  "l1_tx": "abc123..."
}
```

**Error responses:**
- `404` — wallet is not a winner / market not yet settled
- `409` — already claimed (returned from L1)
- `502` — L1 node unreachable

**UI flow:**
1. On mount of a resolved market page, call `GET /api/wallet/bb` to get the user's Solana wallet address
2. Call `GET /api/proof/:market/:wallet` — if `proof.length > 0`, user is a winner
3. Show a "Claim {payout_bb} BB" button
4. On click, `POST /api/markets/:id/claim { wallet }`
5. Display success with `l1_tx` hash or error message

### 2. User Share Position Display (Milestone 5) — [FRONTEND]

Logged-in users can see how many shares of each outcome they currently hold in a live BB market.

**Endpoint (already existed):**
```
GET /api/markets/:id/shares/:username
```

**Response:**
```json
{
  "market_id": "MLS-W8-LAFC-MIA",
  "username": "alice",
  "shares": {
    "LAFC": 15.0,
    "Draw": 0.0,
    "Miami": 5.5
  }
}
```

**UI flow:**
1. On mount of an active market page, call `GET /api/auth/me` to get `username`
2. Call `GET /api/markets/:id/shares/:username`
3. Filter out outcomes with `shares <= 0`
4. Display as pill badges: `LAFC · 15.00 shares`
5. Clicking a pill selects that outcome and pre-fills the sell input

**Refresh:** Call again after any successful buy or sell to update the display live.

## L1 Client Method Added (`prism/src/lib/bb/l1-client.ts`) — [L2 SERVER]

> ⚠️ **CORRECTED from earlier draft** — The field is `amount` in **lamports** (5 decimals,
> `100_000 = 1 BB`), not `payout_spl` in 6-decimal SPL units. The L1 `/escrow/withdraw`
> endpoint expects `amount: u64` measured in lamports. Sending SPL units (10× larger)
> will cause merkle proof verification to fail every time.

```ts
l1Claim(body: {
  contest_id: string;
  winner_wallet: string;        // base58-encoded 32-byte Solana pubkey
  merkle_proof: string[];       // hex-encoded SHA-256 sibling hashes (no 0x prefix needed; 0x is stripped)
  amount: number;               // ← LAMPORTS (100_000 = 1 BB, NOT 1_000_000)
  public_key: string;           // hex 32-byte Ed25519 pubkey
  signature: string;            // hex 64-byte Ed25519 sig over canonical message
  timestamp: number;            // unix seconds (rejected if >60s old)
  nonce: string;                // unique string (replay protection)
})
// Canonical message signed by winner:
// "ESCROW_WITHDRAW:{contest_id}:{winner_wallet}:{amount}:{timestamp}:{nonce}"
// where {amount} is the same lamports integer sent in the body.
// → { success, tx_hash?, error? }
```

## Rollup Block Number Persistence (Rust) — [L2 SERVER]

`l2_block_number` is now persisted to redb on every BB market resolution. This prevents the L1 replay guard from failing after a dealer restart (L1 rejects block numbers ≤ last seen).

No frontend impact — purely a reliability fix on the server side.

## L2 Merkle Tree Requirements — [L2 SERVER]

The L1 escrow contract verifies proofs with this exact leaf construction. The L2 **must** build its tree identically or proofs will never pass.

### Leaf hash
```
leaf = SHA256(
    pubkey_raw_32_bytes         // base58-decode the winner wallet → raw [u8; 32]
  || amount_spl_u64_le_bytes    // amount_spl = lamports × 10  (converts 5-decimal → 6-decimal)
)
```
**Example:** winner wallet `9B5X…` holds a 12.5 BB payout.
- lamports = `12.5 × 100_000 = 1_250_000`
- amount_spl = `1_250_000 × 10 = 12_500_000`
- leaf = `SHA256(raw_pubkey_bytes || 12_500_000u64.to_le_bytes())`

> ⚠️ **Why the ×10?** L1 BB uses 5 decimals (`LAMPORTS_PER_BB = 100_000`) but the escrow Merkle
> leaf was designed around 6-decimal SPL units. L1 applies `lamports × 10` internally before hashing.
> The L2 must use the **same** 6-decimal amount when building leaves.

### Branch combine (sorted hashing)
```
parent = SHA256(min(left, right) || max(left, right))
```
Always put the smaller `[u8; 32]` first (lexicographic). This makes the tree order-independent.

### State root submission signing format — [L2 SERVER]
When the L2 dealer calls `POST /escrow/submit-state-root`, it signs a **binary** message, not UTF-8:
```
signed_bytes = contest_id.as_bytes()
            || l2_block_number.to_le_bytes()   // 8 bytes little-endian u64
            || merkle_root                     // 32 raw bytes
```
The L1 verifies the above concatenation against the `signature` + `sequencer_pubkey` fields.

## Notes for Other Frontend Implementations — [FRONTEND]

- **Wallet address vs username:** Share positions use L2 `username`. Merkle proofs use the Solana `wallet address` (base58). These are different — do not mix them up.
- **Amount units:** The L1 `amount` field in `l1Claim` is in **lamports** (5 decimals). `1 BB = 100_000 lamports`. Display payout as `amount / 100_000`. Do **not** use `1_000_000` as the divisor — that is SPL units and will show values 10× too small.
- **Proof depth:** A market with N winners has a Merkle tree of depth `ceil(log2(N))`. A single winner has proof depth 0 (empty array is still a valid proof — L1 accepts it: the leaf is compared directly to the root).
- **Already claimed:** L1 returns `409` if the winner already submitted this proof. Show "Already claimed" rather than an error.
- **Sell endpoint path:** The L2 sell route is `/bb/:id/sell`, not `/markets/:id/sell`. The Next.js route at `/api/markets/:id/sell` translates this correctly via `l2.sellShares`.
- **Proof hex format:** Sibling hashes may optionally include a `0x` prefix — L1 strips it automatically. Prefer no prefix for consistency.
